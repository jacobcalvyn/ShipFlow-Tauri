# Native Runtime Readiness and Release Smoke Checklist

This checklist separates the current completion target from the future signed
production release gate. The current target is **native runtime readiness before
signing**. It proves the Desktop and Service runtime behavior without claiming a
production signed release.

Signed production distribution is deferred until Apple Developer ID,
notarization credentials, Windows code-signing certificate, a Windows runtime
test machine, and updater signing credentials are available.

## Current Completion Scope

- macOS local/dev installed smoke evidence passes for Desktop and Service native
  runtime behavior.
- Windows Desktop and Service GitHub Actions build artifacts pass without
  requiring signing secrets.
- `Quality Gate` passes, including source checks, `security:baseline`, and
  `test:native-runtime-evidence`.
- Native evidence verifier scripts pass against collected macOS local/dev smoke
  evidence.
- Signing, notarization, Windows manual runtime smoke, and signed updater
  validation are explicitly tracked as deferred production-release work.

## Readiness Artifacts

- macOS local/dev `ShipFlow Desktop.app` and `ShipFlow Service.app` artifacts for
  local smoke testing.
- Windows GitHub Actions artifacts from `Build Desktop Windows` and
  `Build Service Windows`. By default these workflows produce readiness
  artifacts without Windows signing secrets.
- macOS local/dev native runtime evidence bundle collected by
  `scripts/macos/collect-native-runtime-evidence.sh`.
- Native evidence verifier output from `scripts/verify-native-runtime-evidence.mjs`.

## Deferred Production Release Artifacts

These items are not required to close the current readiness goal. They become
mandatory only when `signed_release=true` is used and the required credentials
and target OS access are available.

- Signed and notarized `ShipFlow Desktop.app` on macOS.
- Signed and notarized `ShipFlow Service.app` on macOS.
- Signed `ShipFlow-Desktop-Setup.exe` on Windows.
- Signed `ShipFlow-Service-Setup.exe` on Windows.
- Signed updater artifacts for every target/platform pair:
  `shipflow-desktop-macos-updater-artifacts`,
  `shipflow-desktop-windows-updater-artifacts`,
  `shipflow-service-macos-updater-artifacts`, and
  `shipflow-service-windows-updater-artifacts`.
- Release evidence manifests generated by `scripts/generate-release-evidence.mjs`
  and verified by `scripts/verify-release-evidence.mjs` for every signed
  distribution and updater artifact set:
  `shipflow-desktop-macos-distribution.evidence.json`,
  `shipflow-desktop-windows-distribution.evidence.json`,
  `shipflow-service-macos-distribution.evidence.json`,
  `shipflow-service-windows-distribution.evidence.json`,
  `desktop-macos-updater.evidence.json`,
  `desktop-windows-updater.evidence.json`,
  `service-macos-updater.evidence.json`, and
  `service-windows-updater.evidence.json`.
- Each signed release evidence manifest must include native `verification` metadata.
  macOS signed evidence must include `codesignVerify`, `spctlAssess`,
  and `staplerValidate`. Windows signed evidence must include `signtoolVerify`.
- macOS `codesign`, `spctl`, `xcrun stapler validate`, and Windows
  `signtool verify /pa /v` evidence.

## macOS Desktop

- Install or run `ShipFlow Desktop.app` from the local/dev build artifact for
  readiness. Repeat this from the signed release artifact once Apple Developer
  ID and notarization credentials are available.
- Launch Desktop from Finder, then launch it again from Finder or `open -b`.
- Confirm the second launch focuses the existing Desktop app instead of creating
  a second UI process.
- Resize and move the main window, quit with `Cmd+Q`, relaunch, and confirm the
  saved window size and position are restored.
- Use the native app menu and confirm About, Preferences, Hide, and Quit use
  macOS-native menu behavior.
- Capture `desktop-runtime-log.txt` after opening Preferences from the native
  macOS app menu and quitting with `Cmd+Q`. The log must include
  `[ShipFlowDesktopMenu] command show-settings emitted` and
  `[ShipFlowDesktopMenu] native quit requested`.

## macOS Service

- Install or run `ShipFlow Service.app` from the local/dev build artifact for
  readiness. Repeat this from the signed release artifact once Apple Developer
  ID and notarization credentials are available.
- Enable `Start ShipFlow Service at login`.
- Confirm `~/Library/LaunchAgents/com.shipflow.service-login.plist` is created
  and launches the Service login autostart entry through `/usr/bin/open -b
  com.shipflow.service --args --shipflow-service-autostart`.
- Confirm the Service login LaunchAgent does not pass `open -n`; login
  autostart must activate the installed Service app idempotently instead of
  forcing a new instance.
- Confirm `launchctl print gui/$UID/com.shipflow.service-login` shows the
  LaunchAgent is registered after enabling `Start ShipFlow Service at login`.
- Disable `Keep running in menu bar`, restart or log out and back in, and
  confirm the API runtime starts without showing a settings window or menu-bar
  item.
- Enable `Keep running in menu bar`, restart or log out and back in, and confirm
  login autostart starts the Service plus exactly one menu-bar companion without
  showing a duplicate settings window.
- Click the menu-bar entry repeatedly and confirm it focuses or recreates one
  settings window only.
- Close the settings window while tray mode is enabled and confirm the window is
  hidden while the Service remains available.
- Quit from the native menu or tray menu and confirm the API runtime, tray
  companion, and settings UI all stop.
- Capture `service-runtime-log.txt` after opening Preferences from the Service
  native menu and quitting from the Service native menu. The log must include
  `[ShipFlowServiceMenu] open preferences succeeded` and
  `[ShipFlowServiceMenu] quitting ShipFlow Service`.

## Windows Desktop

- Install `ShipFlow-Desktop-Setup.exe` from the Windows GitHub Actions artifact.
  This can be unsigned for readiness; signed installation verification is
  deferred until a Windows signing certificate and Windows runtime test machine
  are available.
- Confirm `HKLM\Software\ShipFlow\Desktop` contains `InstallLocation` and
  `ExecutablePath` pointing to the installed Desktop directory and executable.
- Launch Desktop twice from shortcuts or Explorer.
- Confirm the second launch delegates through the named mutex and activation
  request, focusing the existing Desktop UI instead of creating a second UI
  process.
- Close the Desktop window and confirm Windows keeps the app available from a
  user-visible tray/taskbar surface instead of orphaning a hidden process.
- Reopen Desktop from that Windows surface and confirm the same UI process is
  focused or recreated without starting a duplicate process.
- Quit Desktop from the explicit Windows exit action and confirm the Desktop UI
  process stops.
- Capture `desktop-runtime-log.txt` after closing the main window to tray,
  reopening Desktop from the tray, and quitting from the tray. The log must
  include `[ShipFlowDesktopTray] main window hidden to tray`,
  `[ShipFlowDesktopTray] open desktop requested`, and
  `[ShipFlowDesktopTray] quitting ShipFlow Desktop`.
- Resize and move the main window, quit, relaunch, and confirm the saved window
  size and position are restored.

## Windows Service

- Install `ShipFlow-Service-Setup.exe` from the Windows GitHub Actions artifact.
  This can be unsigned for readiness; signed installation verification is
  deferred until a Windows signing certificate and Windows runtime test machine
  are available.
- Confirm `HKLM\Software\ShipFlow\Service` contains `InstallLocation` and
  `ExecutablePath` pointing to the installed Service directory and executable.
- Enable `Start ShipFlow Service at login`.
- Confirm `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` contains the
  `ShipFlowService` value pointing to the installed Service executable with
  `--shipflow-service-autostart`.
- Disable `Keep running in system tray`, restart Windows, and confirm the API
  runtime starts without showing a settings window or system-tray icon.
- Enable `Keep running in system tray`, restart Windows, and confirm login
  autostart starts the Service plus exactly one system-tray companion without a
  duplicate settings window.
- Click the tray icon and `Open ShipFlow Service` repeatedly and confirm only one
  settings UI is focused or recreated.
- Use tray `Open ShipFlow Desktop`, `Copy Endpoint`, `Restart API`, and `Quit
  ShipFlow Service` repeatedly and confirm the actions are idempotent. Capture
  runtime logs showing `open service settings succeeded`, `open desktop succeeded`,
  `copy endpoint succeeded`, `restart API succeeded`, and
  `[ShipFlowServiceTray] quit requested`.
- Uninstall `ShipFlow Service` and confirm the `ShipFlowService` Run entry and
  legacy `ShipFlowServiceTray` Run entry are removed.

## Updater

Signed updater validation is deferred for the current readiness goal. Run this
section only after updater signing credentials and a signed distribution channel
are available.

- Run the `Build Updater Artifacts` workflow and confirm the matrix creates
  Desktop macOS, Desktop Windows, Service macOS, and Service Windows updater
  artifact sets in one release gate.
- Confirm each updater artifact set includes non-empty `.sig` files with a
  matching non-empty signed artifact.
- Confirm each updater artifact set includes its matching updater evidence
  manifest and that every `.sig` entry has a `signatureFor` value.
- Confirm macOS updater sets include both `.app.tar.gz` and `.dmg` signed
  artifacts plus matching `.sig` files.
- Confirm Windows updater sets include a signed installer artifact plus the
  Windows installer updater signature.
- Publish signed updater metadata for Desktop and Service to the configured
  HTTPS updater endpoint.
- From installed Desktop, run Check for Updates and Install Available Update.
- From installed Service settings, run Check Update and Install Update.
- Confirm the updated installed app remains signed and, on macOS, notarized.
- Confirm macOS updater artifacts include stapled notarization tickets for both
  the `.app` bundle and any generated DMG installer.

## Evidence

Attach the following evidence to the readiness checklist or pull request:

- CI run URLs for `Quality Gate`, `Build Desktop Windows`, and
  `Build Service Windows`.
- macOS local/dev smoke evidence bundle and verifier output.
- Distribution evidence manifests for signed Desktop macOS, Desktop Windows,
  Service macOS, and Service Windows are deferred until `signed_release=true`.
- Windows distribution artifacts for Desktop and Service must attach both the
  signed executable (`shipflow3-tauri.exe` or `shipflow-service.exe`) and the
  signed setup installer.
- Every signed distribution build must use the updater-ready release config:
  `TAURI_UPDATER_PUBLIC_KEY` and non-empty HTTPS `TAURI_UPDATER_ENDPOINTS` must
  be injected into the app config before building the installer.
- Updater evidence manifests for Desktop macOS, Desktop Windows, Service macOS,
  and Service Windows.
- Evidence manifest excerpts proving every attached signed installer/updater
  artifact has `bytes` and `sha256`, and every updater `.sig` entry has
  `signatureFor`. Windows distribution excerpts must show both the signed app
  executable (`shipflow3-tauri.exe` or `shipflow-service.exe`) and the signed
  setup installer. Every release evidence manifest must include
  `updaterConfig.publicKeySha256` and non-empty HTTPS
  `updaterConfig.endpoints`; updater evidence must also include top-level
  `updaterEndpoints` matching the metadata publication target.
- macOS `codesign`, `spctl`, `xcrun stapler validate`, and updater
  installation output.
- macOS evidence bundle collected with
  `scripts/macos/collect-native-runtime-evidence.sh` after enabling
  `Start ShipFlow Service at login`. Pass `1` as the fourth argument on a test
  machine when collecting the repeated Desktop launch single-instance evidence,
  and pass `1` as the fifth argument for repeated Service Settings launch
  single-instance evidence. Pass `1` as the sixth argument for
  repeated Service tray launch single-instance evidence. The repeated-launch evidence must
  include `desktop-runtime-log.txt`, `service-runtime-log.txt`,
  `service-tray-runtime-log.txt`, and `service-tray-single-instance-processes.txt`
  proving the existing app consumed duplicate Desktop/Settings launches and
  duplicate tray launches are skipped without a second tray companion.
- macOS evidence bundle verified with
  `node scripts/verify-native-runtime-evidence.mjs macos release-smoke-evidence/macos --require-repeated-launch --require-tray-actions --require-tray-single-instance --require-window-state --require-menu-actions`.
- macOS `PlistBuddy` output proving `CFBundleIdentifier` and
  `CFBundleExecutable` for Desktop and Service.
- macOS `desktop-launchservices-discovery.txt` and
  `service-launchservices-discovery.txt` proving LaunchServices resolves
  `com.shipflow.desktop` and `com.shipflow.service` back to the installed app
  paths used by the smoke collector.
- macOS `launchctl print gui/$UID/com.shipflow.service-login` output after
  enabling Service login autostart.
- Windows `signtool verify /pa /v` output for both executables and installers is
  deferred until a Windows signing certificate is available.
- Windows evidence bundle collected with
  `scripts/windows/collect-native-runtime-evidence.ps1` after enabling
  `Start ShipFlow Service at login`. Pass `-DesktopInstallerPath` and
  `-ServiceInstallerPath` so the evidence bundle includes signed installer
  verification output. Use `-LaunchDesktopTwice` on a test machine when
  collecting repeated Desktop launch single-instance evidence, and use
  `-LaunchServiceSettingsTwice` for repeated Service Settings launch
  single-instance evidence. Use `-LaunchServiceTrayTwice` for repeated Service
  tray launch single-instance evidence. The repeated-launch evidence must
  include `desktop-runtime-log.txt`, `service-runtime-log.txt`,
  `service-tray-runtime-log.txt`, and `service-tray-single-instance-processes.txt`
  proving the named mutex delegated activation to the existing UI and duplicate
  tray launches are skipped without a second tray companion. Windows
  `desktop-runtime-log.txt` must include `[ShipFlowDesktopTray] Windows tray ready`
  so the close-to-tray path is proven against an installed Desktop
  runtime, not only source inspection. When `--require-tray-actions` is used,
  the same file must also include `[ShipFlowDesktopTray] main window hidden to tray`,
  `[ShipFlowDesktopTray] open desktop requested`, and
  `[ShipFlowDesktopTray] quitting ShipFlow Desktop`.
- Windows evidence bundle verified with
  `node scripts/verify-native-runtime-evidence.mjs windows release-smoke-evidence/windows --require-repeated-launch --require-tray-actions --require-tray-single-instance --require-window-state`.
- The evidence package must include repeated Service Settings launch single-instance evidence when those optional collector flags are used.
  It must also include `service-tray-single-instance-processes.txt` and a
  `duplicate tray launch skipped` runtime log when the Service tray
  single-instance collector flag is used.
- Windows `reg query HKLM\Software\ShipFlow\Desktop` and
  `reg query HKLM\Software\ShipFlow\Service` output proving stable
  `InstallLocation` and `ExecutablePath` discovery values.
- Windows `desktop-executable-discovery.txt` and
  `service-executable-discovery.txt` proving each registry `ExecutablePath`
  matches the executable verified by the smoke collector.
- Windows `reg query HKCU\Software\Microsoft\Windows\CurrentVersion\Run` output
  proving the explicit `ShipFlowService` autostart value, plus evidence that
  the legacy `ShipFlowServiceTray` Run value is absent.
- Screenshots or logs proving single-instance focus and tray/menu behavior on
  both platforms, including the repeated-launch runtime log evidence above.
- macOS native menu runtime logs proving Desktop Preferences, Desktop native
  quit, Service Preferences, and Service native quit were exercised from the
  installed apps. Verify this with `--require-menu-actions` so
  `desktop-runtime-log.txt` must contain
  `[ShipFlowDesktopMenu] command show-settings emitted` and
  `[ShipFlowDesktopMenu] native quit requested`, and `service-runtime-log.txt`
  must contain `[ShipFlowServiceMenu] open preferences succeeded` and
  `[ShipFlowServiceMenu] quitting ShipFlow Service`.
- Windows Desktop tray runtime logs proving close-to-tray, tray reopen, and tray
  quit were exercised from the installed app. Verify this with
  `--require-tray-actions` so `desktop-runtime-log.txt` must contain
  `[ShipFlowDesktopTray] main window hidden to tray`,
  `[ShipFlowDesktopTray] open desktop requested`, and
  `[ShipFlowDesktopTray] quitting ShipFlow Desktop`.
- `window-state.json` and `window-state-source.txt` proving the installed app
  persisted usable `desktop.main` and `service.settings` window state after the
  resize/move/relaunch smoke checks. The source file must come from the current
  installed runtime state directory (`ShipFlow Service/shipflow-service-runtime`),
  not a temporary or legacy Desktop state directory.
- Service tray runtime logs proving repeated tray commands succeed without
  spawning duplicate UI processes or leaving the API runtime in an inconsistent
  state. Verify this with `--require-tray-actions` so
  `service-tray-runtime-log.txt` must contain `open service settings succeeded`,
  `open desktop succeeded`, `copy endpoint succeeded`, `restart API succeeded`,
  and `[ShipFlowServiceTray] quit requested`.
- Service tray single-instance evidence proving repeated tray companion launch
  leaves exactly one `--shipflow-service-tray` process. Verify this with
  `--require-tray-single-instance` so
  `service-tray-single-instance-processes.txt` must contain exactly one tray
  process record and `service-tray-runtime-log.txt` must contain
  `duplicate tray launch skipped`.
